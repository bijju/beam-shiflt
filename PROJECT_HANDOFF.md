exactly 619px throughout. This is the honest mathematical limit — don't
re-attempt margin/separation tuning to close a width-bound board's gap
further; the real fix for future content is choosing board shapes that
aren't width-bound (recorded generator guidance: prefer taller profiles
like 5x9/6x10/7x11/8x11). Full resolution/profile matrix unchanged at
140/140 comfortable. Visually confirmed via 6 real rendered levels/
tutorial. Full regression unchanged: 188/188 PASS; Phase 2 re-check:

**"Full-Screen Board Correction"** (previous, `versionCode=43`,
`versionName="3.6.1-FULLSCREEN-BOARD-QA"`). See `DECISIONS.md` D86 for
the full writeup. **Corrects a real bug Phase 1 (D84) shipped**: the
user tested `versionCode=42` on a real phone and found Level 27 (7x8)
rendering with large wasted vertical space and a small, centered board.
Root cause: Phase 1 validated its layout math only at the 1080x1920
reference and never rendered a real campaign level at the other 4
required resolutions — `canvas_items`/`expand` reveals more logical
canvas height on taller devices (most real phones), and a width-bound
board's `cell_size` doesn't grow to compensate, so height utilization
silently degrades with zero level/code change (94.2%→64.7% for Level 27
between 1080x1920 and 1080x2400). **Fix**: `SafeAreaMargin` gained a
`margin_override` field; `game.tscn` now uses a smaller, gameplay-
specific baseline (`UIConstants.GAMEPLAY_BASELINE_MARGIN := 32.0` vs.
the menu-tuned `96.0`, which every menu screen keeps unchanged). Real
Android safe-area insets still widen it via the existing `maxf()`
logic. **Result**: Level 27's cell_size 124px→142px (+14.5%), height
utilization 64.7%→72.3%; full resolution/profile matrix now 140/140
comfortable (up from 136/140), visually confirmed via 5 real rendered
levels/tutorial. **Honestly disclosed**: a width-bound board's
`cell_size` was already width-maximized — some residual gap on very
tall devices for boards authored against the 1920 floor remains
mathematically unavoidable without a level redesign or non-square
cells (both out of scope this pass). Full regression unchanged:
188/188 PASS; a dedicated Phase 2 re-check: 12/12 PASS. **NOT MANUALLY
APPROVED — Android device QA pending.**

## Level editor (Milestone 3)

**Not part of the shipped game** — a plain runtime scene
(`tools/level_editor/level_editor.tscn`, no `@tool`, no `EditorPlugin`),
opened by running it directly in the Godot editor (F6), excluded from
the Android export filter. See `LEVEL_EDITOR.md` for full usage and
`ARCHITECTURE.md`'s "Editor architecture" section plus `DECISIONS.md`
D23 for why this architecture was chosen over an EditorPlugin/dock.

Reuses `LevelData`/`TilePlacement`/`LaserSystem` completely unchanged.
Adds three new pure-logic classes:

- **`LevelSolver`** (`scripts/tools/level_solver.gd`) — a real
  breadth-first search over every combination of rotatable mirror/
  splitter orientations, evaluating each candidate with the actual
  `LaserSystem` (never an approximate second simulator). Reports
  solvability (`SOLVABLE`/`UNSOLVABLE`/`UNKNOWN` — the last meaning the
  search's safety limit was hit, explicitly not the same claim as
  unsolvable), optimal move count, how many distinct shortest solutions
  exist, one example solution path, and "possible decoy" pieces (see
  `ARCHITECTURE.md`/`DECISIONS.md` D26/D27).
- **`LevelValidator`** (`scripts/tools/level_validator.gd`) — structural
  checks (missing emitter/target, out-of-bounds or duplicate tiles,
  invalid portal pairing, dangling switch→gate references) as hard
  errors that block Save/Playtest, plus advisory warnings (no rotatable
  pieces, very high tile count, an unopenable gate, a zero-move trivial
  solution).
- **`LevelMetrics`** (`scripts/tools/level_metrics.gd`) — tile/mechanic
  counts and a transparent, explicitly-non-authoritative difficulty
  estimate (see `DECISIONS.md` D28 for the exact formula).

Levels can now be saved/loaded as `.tres` Resource files
(`LevelManager.load_level_from_path()` handles both `.tres` and the
existing `.gd` format transparently) — see `DECISIONS.md` D25 for why
this is safe now in a way hand-authoring `.tres` wasn't for Milestone 1
(D1), and why Levels 1–15 were deliberately left as `.gd` files rather
than migrated.

## Multi-beam simulator architecture (Milestone 2)

Unchanged by Milestone 3. Full detail in `ARCHITECTURE.md`'s "Laser
